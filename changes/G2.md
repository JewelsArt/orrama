## Changelog lines (user-facing, for [Unreleased] → Fixed / Internal)

Fixed
- Uploading a document whose name has `" * : < > ? |`, ends in a dot or a space, or is a name
  Windows keeps for a device (CON, NUL, COM1…) is refused with the reason, on every computer, so a
  vault made on the Mac still opens on Windows. On Windows such an upload failed, or for a device
  name stored nothing. Files already in your vault keep opening.
- Stopping the server closes the database after the vault watcher, not before (a file changed in
  the last moment could hit a closed database).
- The server's log rotates on Windows too (it truncated through a handle Windows opens append-only).

Internal
- The server suite runs green on Windows (windows.yml also runs the webhook tests 20 times in a row
  and starts the dev server); a test file that leaves a database open fails on every platform.
- Every MCP tool has a test of the request it sends and of the server's answer.

## Not done (and why) / needs Jules
- **Note names, same class, not fixed**: New note, a move or the agent can still make a note
  named `Why now?.md` or `re: v2.md`; on Windows that fails (500) or writes into a hidden stream.
  Refusing those for notes is a wider change than uploads (the vault already holds such names,
  Obsidian refuses `?` and `:` in its own UI). Prompt for its own session:
  `~/basalt-followups/note-names-windows.md`.
- **Two watcher tests can lose an event under heavy load** on macOS (seen once each while other
  sessions ran suites, load ~130+): path-identity's NFD case (25 s, its third timeout raise) and
  new-folder-watch's gap case. Both pass alone and on rerun (6/6, 3/3). Not changed: their timeouts
  are already long, and a lost FSEvents event is not something a test-side wait can fix.
- Log rotation on Windows: if the Windows run **skips** the two rotation tests, that platform
  cannot stat an append-mode handle and rotation stays off there (the server cannot tell its stdout
  is the log). Fine for Basalt (the agent is launchd, macOS), worth knowing.
- The debounce of webhook deliveries has no test that can see it (one save is one event); a
  two-save test at the suite's 40 ms debounce would be timing-bound.
