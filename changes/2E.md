## Built

- **Schema copy before an upgrade** (commit 1, `87c7f41`): `createDb` copies a database whose
  `user_version` is below `SCHEMA_VERSION` and which has tables to
  `<data dir>/backups/basalt-schema-<old>-<UTC date>-<hhmmss>.db` (VACUUM INTO, one file, mode 600,
  folder 700), keeps the newest three `basalt-schema-*`, leaves anything else there alone, and
  upgrades nothing when the copy fails. The newer-database refusal names the folder. For every
  install, Jules's too (`apps/server/data/backups` appears on his next schema bump).
- **The updater** (commit 2, `00c3765`): `tauri-plugin-updater` ~2.12.0 (the last line on tauri 2.11) with
  native TLS (no rustls: its root-certificate crate is CDLA-Permissive-2.0, outside our licence
  list), driven from Rust only (`src-tauri/src/updater.rs` + `AppFeed` in `lib.rs`; no capability
  grants a page any of its commands). The feed is
  `https://github.com/JewelsArt/orrama/releases/latest/download/latest.json` (D1's recommended repo;
  one line in `tauri.conf.json` if 2G names it otherwise). Downloads before asking, signature
  checked against the public key. Restart now = the supervisor's stop (stdin closed, wait, kill
  after 10 s) → install → `request_restart`; a failed install starts the old app again. A pre-release
  (`-test.N`) or an older version is never offered. Debug builds never check. Windows install mode
  `passive`. `createUpdaterArtifacts: true`.
- **The feed** (commit 3): `scripts/release-feed.mjs` (`add` puts one platform's signed bundle into
  `latest.json`, notes from the version's CHANGELOG entry; `check` before publishing; refuses mixed
  versions, test builds, missing signatures, non-https downloads). `release-build.mjs` signs when
  `TAURI_SIGNING_PRIVATE_KEY`(+`_PASSWORD`) are set, else builds with no update bundle and says so;
  `--config <json>` merges a test build's version/feed/key. `release.yml`: the key only in the build
  step's env, an "update feed" step in both jobs (a tag run without the key fails, a run by hand
  without it is a test build with no feed), the mac job `needs: windows` (one writer of
  `latest.json`), publishing stays Jules's. README "Updates" has the release in order.

## Proved on the Mac (27 Oct)

Two release builds with the throwaway key and a scratch config (`--config`: version, feed
`http://127.0.0.1:4879/latest.json`, `dangerousInsecureTransportProtocol`, test pubkey): 0.1.90, and
0.1.91 whose server had `SCHEMA_VERSION = 6` (set in the working tree for that build only, put back,
`git diff` clean). The thirteen version places were left alone: the version came from the override.

1. 0.1.90 copied into `~/basalt-scratch/2E/Applications`, opened with scratch HOME, data, notes. No feed
   up: "couldn't look for a new version: error sending request…" in the log, app fine.
2. Account (sam@example.test), Start empty, a note, Clay at night, through the server's API on the
   app's port (63393; the browser pane was hidden). user_version 5.
3. `release-feed.mjs add` + `check --platforms darwin-aarch64` → local feed served. Relaunch: "Orrama
   0.1.91 is out: downloading it" → "downloaded and its signature checks out".
4. **The dialog** (Jules's screenshot): macOS's own alert, title "Orrama", the text "Orrama 0.1.91 is
   ready." then "Fixed", "• Notes keep their place after an update", "• The month view counts every
   event" (the 4th and 5th lines left out), buttons **Later** and **Restart now** (default, right).
   Jules clicked Later → "Later, asked again at the next launch"; no second dialog that launch.
5. Relaunch → asked again → Jules clicked Restart now. Log, in order: "Restart now: stopping the
   server, then installing Orrama 0.1.91" → server "stdin closed: closing" → "the server stopped
   (exit status: 0)" → "the new version is installed: starting it" → new server on the same port.
6. After: Info.plist 0.1.91, `codesign --verify --deep --strict` valid, database user_version 6,
   `backups/basalt-schema-5-2026-10-27-133105.db` (mode 600, user_version 5, the account and its
   session), the session cookie from before still signed in, Clay at night kept, the note
   byte-identical, port kept.
7. 0.1.90 put back over the schema-6 database: "…was written by a newer Orrama (schema 6; this build
   knows 5)… restore a backup from …/data/backups."

Measured: `release-build.mjs` 2.3 min after a dependency change (tauri build 130 s), 1.4–1.5 min
warm; max RSS 1.98 GB. `.dmg` 46.1 MB, update bundle `Orrama.app.tar.gz` 47.2 MB, `.sig` 404 bytes.
Download + check ~1 s from localhost.

Not clicked: the window's own sign-in across the update (the window was never signed in; the session
was a cookie jar on the app's port, same server and table). WebKit data under
`~/Library/{Caches,WebKit}/com.orrama.desktop` deleted after the runs; the default app data folder
was never made.

## Not done / follow-ups

- **`requireSignedVersion` is off.** Tauri CLI 2.11.4 writes no `version:` in the signature's
  trusted comment (seen in the test `.sig`: timestamp and file only), and with the flag on the plugin
  refuses every update. Without it, someone who controls `latest.json` (the GitHub account) could
  pair a newer version number with an older genuine build. Turn it on once the toolchain moves to a
  CLI that records the version (2.12.x may; it needs tauri 2.12).
- The release notes in the dialog are the CHANGELOG entry's first lines: its `### Added` heading
  shows as "Added". Fine for now; a short "notes for friends" line per release would read better.
- The test builds' config override is the way to test locally; the shipped app has no env override
  of its feed.
