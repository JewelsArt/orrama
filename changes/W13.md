# W13: the login session moves into a secure cookie (WEB-013, stage 0)

## Built
- Every signed-in request goes out through one place, `sessionFetch` in `api.ts` (api(), apiBlob, Ask Orr's stream, the keepalive save); a 401 from Ask Orr now signs the app out like any request (commit a3b8739)
- Sign-in sets the `orrama_session` cookie: HttpOnly, SameSite=Strict, Path=/, Max-Age 30 days, Secure only when the page came over https; sign-out, sign out everywhere and ending your own session clear it. `authenticate` reads the session from the cookie; `Bearer bslt_…` is unchanged; a write the cookie carries needs our own `Origin` (`fromOwnSite`), else 403. `POST /api/auth/exchange` trades a token kept from before the cookie for the cookie, once (38b367f)
- Server tests sign in through the cookie: `test/helpers/session.ts` (`sessionOf`, `signedIn`, `liveSocket`, `refusedWith`); mechanical over 79 files (6fd036c)
- Sign-in answers `{ user }` only (`signInResponse` in packages/schema, contract-tested); live sync signs in on the upgrade from the cookie, with an Origin check, and the first-frame auth is gone; the web app keeps no token, trades a kept one at boot (`adoptStoredSession`), and a socket refused before it opens asks /api/me once so an ended session signs out (00d7c84)
- These notes (this commit)

## Audit tickets fixed
- WEB-013: both acceptance criteria hold. No session credential is readable from `document.cookie`, Web Storage or any response body (sign-up, password, passcode, Touch ID, exchange); AskPanel and the socket use the same auth as `api()`, and a 401 from either ends the session in the app. (a3b8739, 38b367f, 00d7c84)

## Changelog lines (user-facing, for [Unreleased])
- Changed: Your sign-in is now kept in a secure cookie the page itself can't read, instead of in the browser's storage. Nothing to do: the first time the app opens after the update, it moves your existing sign-in over by itself.
- Changed: Live sync signs in when it connects, from that cookie, and only from Orrama's own pages.

Under "Upgrading" in the version's entry: the next release stops accepting a session token sent as `Bearer` and drops `/api/auth/exchange`. A browser, window or phone not opened once on this release will have to sign in again then.

## CLAUDE.md changes to apply (exact text, and where)

1. Conventions & gotchas, replace the paragraph **"A session is a row, not just a signature"** with:

- **A session is a row, not just a signature** (`apps/server/src/sessions.ts`),
  **and the browser never holds it** (WEB-013). Every sign-in opens a `sessions`
  row and sets the `orrama_session` cookie — HttpOnly, SameSite=Strict, Path=/,
  30 days, Secure when the page came over https (never on http://localhost,
  where WebKit refuses it) — holding a JWT that names the row (`sid`). No
  response body carries a session (sign-in answers `signInResponse`, `{ user }`).
  The auth hook and the live-sync socket refuse a session whose row is gone or
  revoked. A write the cookie carries (anything but GET/HEAD/OPTIONS) needs an
  `Origin` that is one of `ORRAMA_PUBLIC_ORIGINS` or the address it was sent to
  (`fromOwnSite`, `routes/auth.ts`), else 403: with SameSite=Strict and the Host
  allow-list, that is the CSRF answer, so a new state-changing route needs
  nothing more — but it must not be a GET. Sign-out (`POST /api/auth/logout`)
  revokes on the server and clears the cookie, Settings → Signed in revokes the
  others, and a revoked session's socket is closed at once. Anything new that
  issues a session goes through `signIn` in `routes/auth.ts`. A token without a
  `sid` is refused. In the web app every request goes through `sessionFetch`
  (`api.ts`), same-origin; the page only keeps whether it counts itself signed
  in (`sessionStarted`/`sessionOver`). For this release only, a session token
  sent as `Bearer` is still accepted and `POST /api/auth/exchange` trades one
  (kept in `orrama-token` by the app before the cookie) for the cookie once
  (`adoptStoredSession` at boot); both go in the next stage. Server tests sign
  in with `test/helpers/session.ts` (`sessionOf`, `signedIn`, `liveSocket`).

2. Conventions & gotchas, **"API tokens are the weaker credential"**: add one sentence at the end of the paragraph:

  An API token is the only credential sent as `Authorization: Bearer`; a
  session is the cookie (see **A session is a row**).

3. **Live sync** section, replace its last two sentences ("Frames from a client are capped at 16 KiB … before it is known to be a valid auth.") with:

  The socket signs in on the upgrade, before it opens, from the session cookie
  and an `Origin` of our own (`signInSocket`, routes/ws.ts): refused, the
  handshake gets 401/403/421 and no socket is made, so the client never sends a
  credential. A browser sees a refused handshake only as a 1006 close, so
  `ws.ts` asks `GET /api/me` once when a socket closes before it opened: a 401
  there signs out (`api.ts`), anything else is retried. Frames from a client are
  capped at 16 KiB (`WS_MAX_FRAME`, `main.ts`): a client only sends presence
  pings, and an auth frame from an app older than the cookie is ignored.

4. Conventions & gotchas, **"Storage"**: replace "and `migrateLegacyKeys()` (first thing in `main.tsx`) moves any left over, so nobody is signed out." with:

  and `migrateLegacyKeys()` (first thing in `main.tsx`) moves any left over.
  Never a credential: the session is an HttpOnly cookie (WEB-013); the token the
  app kept before it is traded once at boot and deleted (`adoptStoredSession`).

5. Conventions & gotchas, **"The door"**: after "Errors go through `door/voice.ts` …" add:

  A way in answers `{ user }`; `useEnter` and Setup call `sessionStarted()`, and
  the session itself is the cookie the server set.

## Not done (and why) / needs Jules
- **Decision for Jules: the cookie's name.** Cookies are kept per host name, not per port. Two Orrama servers on `localhost` in the same browser (the live :4623 and a dev server, or several sessions' scratch servers in one browser pane) now share one `orrama_session` cookie, and signing in to one signs the other out. localStorage was per port, so this is new. It does not touch the desktop app (its own WebKit store, one server), the phone, or friends (one server each). The fix would be a name per server port (`orrama_session_4623`); I kept the name the prompt gave until Jules decides.
- The next stage drops `Bearer <session token>` in `authenticate` (main.ts), `POST /api/auth/exchange` (routes/auth.ts), `rekeySession` (sessions.ts), `adoptStoredSession` and `LEGACY_TOKEN_KEY` (api.ts) and the tests that exercise them (session-cookie.test.ts "a token kept from before the cookie", session-ended.test.ts, app-door.dom.test.tsx, storage-migration.dom.test.tsx).
- Not testable here, for the integrator after ship:
  1. Touch ID on a real device: enrol and unlock (the browser pane has no authenticator; the verify answer is tested with the authenticator stubbed).
  2. The desktop window after `pnpm ship`: ⌘R must land signed in, through the exchange (Settings → Signed in still shows "Mac · Desktop app" as one row). Before ⌘R the old bundle keeps working on its Bearer token; its live sync stays off until the reload (the upgrade refuses it quietly, it retries).
  3. The phone over Tailscale (https): signs in, the cookie is Secure (Safari's Web Inspector → Storage → Cookies), live sync works. The tailnet name must be in `ORRAMA_PUBLIC_ORIGINS`, as today.
  4. A cross-site check stays green: `curl -b <cookie> -X PATCH -H 'origin: https://evil.example' …/api/me` → 403.
- Seen once under full-suite load: `renamed-env.test.ts` timed out at 5 s (it spawns the scripts); passes alone, unrelated.
