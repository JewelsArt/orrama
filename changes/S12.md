# S12 — Permissions before a second account

Branch `fix/S12-multi-user-acl`, from `sep-2026-redesign` @ e54ae96. Every leak
test is in `apps/server/test/acl-second-account.test.ts` (two teams, one
assertion per leak; release-blocking like the other permission tests), except
ACL-008's, which is core: `packages/core/test/search-rank-acl.test.ts`.

## Fixed

- ACL-002 — a project's note is anchored on its registration (`projects.note_id`, schema 4; `VaultStore.projectNote`), never picked from the caller's readable notes; tagging your own note no longer opens another team's documents, board, name or tasks (commit ea7a2ea)
- ACL-004 — the team dashboard lists only projects whose note (or folder) the reader can read, empty ones included (commit ea7a2ea)
- ACL-005 — a save, create, move or link answers a note the caller cannot read exactly as it answers no note; no hash is compared before the ACL; links, backlinks and graph edges resolve among readable notes (commit ebeec6e)
- ACL-007 — a debounced webhook delivery re-runs the hook owner's ACL on the note as it is when it goes out (commit 299d4c8)
- ACL-010 — removing or renaming an account retires its username (`meta`); sign-up and renames refuse a retired name (commit 4c65045)
- ACL-009 — calendar notes (events and blocks) go to `Personal/<u>/Calendar/` when another account could read `01-Me/Calendar/`; a row in such a note moves out when next written (commit 44ed2b0)
- ACL-008 — search ranks with the reader's own corpus (note count, lengths, document frequencies); an owner keeps the vault-wide counts (commit 2725645)
- ACL-003 — already fixed by COR-003 (6069114, wave B: blocks are the rows of your own calendar notes, on tasks you can read). Reproduced as fixed with the audit script (block booking adapted to the task-by-text API); the ticket's exact scenario is now a leak test, sabotage-checked against the audited assignee query (this commit)

## Changelog lines (user-facing, for [Unreleased] → Fixed / Security / Internal)

Security:
- A project whose note lives outside `04-Projects/` can no longer be opened — documents, board, name — by someone who tags a note of their own with its key; the project's note is fixed when it is registered (ACL-002).
- The team dashboard no longer names projects you cannot read (ACL-004).
- Saving, moving or linking to a note you cannot read answers exactly as if there were no note: no "changed since it was opened", no "already exists", no locked link — and no way to confirm a private note's text by guessing its hash (ACL-005).
- Webhooks check the note again when the delivery goes out, so a note moved or restricted in the debounce window is not sent with its new path and title (ACL-007).
- A removed or renamed account's username is retired: nobody can sign up as it and inherit `Personal/<username>/` (ACL-010).
- Your events and time blocks are written to a calendar note no other account can read — `Personal/<you>/Calendar/` when another account could read `01-Me/` (ACL-009).
- Search result order no longer depends on notes you cannot read (ACL-008).

Upgrading:
- Schema 4 (`projects.note_id`). A database opened by this build refuses to open in an older one. Existing projects are anchored to their note on first use.

Internal:
- `store.projects(user)` takes the reader; `VaultStore.projectNote(key)` is the one way to the note a project is authorised against.
- `VaultIndex.resolveLink/resolveLinkOf` take `among`, the notes a link may name.
- Account removal is `removeAccount.ts` (remove-user.ts is its prompt); retired usernames are `usernames.ts`.

## Not fixed (and why) / needs Jules

- REG-009 (history serves past revisions under the current ACL) — **won't fix**, Jules's decision of 2026-10-02; nothing changed.
- Residuals, by design:
  - ACL-002: a row with no anchor (this upgrade, or a database rebuild) or whose note lost its tag is anchored by the `projectNoteFor` ranking, which a planted note with an older id could win. Jules's database has one account, so nobody could have planted one.
  - ACL-005: where the caller may create a note at a path, a hidden note there still makes the save a refusal instead of a creation — unavoidable.
  - ACL-009: rows already in an exposed `01-Me` note stay until next edited (no boot-time rewrite of the vault).
  - ACL-010: an account deleted by hand in SQL retires nothing (remove-user is the supported path). Refusing any name with a `Personal/<name>/` folder on disk was rejected: after a DB rebuild it would refuse people their own names.
  - ACL-004: `teamId = null` still means "every team" (all tag projects have it; the Projects board depends on it).
- Other instances of "resolve over the whole vault, filter after" seen outside S12's files, not changed: `routes/people.ts:59` (relations by link), `routes/graph.ts:65` (a ref by title), `calendarNotes.ts:286` (a block's task by link), `suggestRelated`'s resolver in `routes/vault.ts:101` and `routes/ai.ts:122` (candidates are readable; the resolver only excludes already-linked notes).
- Flaky under load, not S12's: `test/env.test.ts` (5 s boot timeout) and web `storage.dom.test.tsx` (5 s) each failed once with the machine at load average ~120 and pass alone.
