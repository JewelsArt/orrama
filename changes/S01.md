## Fixed
- STO-001 — an emoji swapped or inserted next to another one no longer writes U+FFFD into the note; splices are whole code points, and a splice that does not land as asked is refused (500, nothing written) instead of saved (commit bbc57b5)
- STO-002 — a leading `---` block that is valid YAML but not a mapping (prose between rules, a list, only comments) is never replaced by an id (commit 9f99855)
- STO-003 — a note whose front matter does not parse, or whose own `id:` is a number, keeps one id across Basalt writes, Obsidian saves and restarts; its task comments, descriptions and status stay attached (commit 9f99855)
- STO-005 — a CRLF note is stamped in CRLF with nothing escaped, and its front matter parses (a last-line flow list is no longer "malformed") (commit 9f99855)
- STO-007 — stamping an id or setting one property changes only that line: no folding at 80 columns, no re-spacing, no re-indenting; a BOM stays at byte 0 (commit 9f99855)
- STO-011 — a note that is not valid UTF-8 (Windows-1252, UTF-16) is indexed read-only: never stamped, never rewritten, a save over it is refused with 409, and the server logs which file and why (Jules chose "refuse + log", 11 Oct) (commit 9f99855)
- STO-004 — the three-way merge no longer glues a line from each side together when the note's last line has no final newline (the commit that adds this file)

## Changelog lines (user-facing, for [Unreleased] → Fixed / Security / Internal)
- Fixed: changing an emoji next to another one (🔴 → 🟢, 🔼 → 🔽, 😀 → 😃) in the editor no longer writes `��` into the note.
- Fixed: Basalt no longer deletes a note's opening `---` block when that block is prose, a list or only comments; such a note is left as written.
- Fixed: a note whose front matter has a YAML error (an unquoted colon), or whose `id:` is a number, keeps the same note id across edits, Obsidian saves and restarts — task comments, descriptions and assignees no longer come loose.
- Fixed: Windows line endings are kept when Basalt adds an id or sets a property, and no `"\r"` is written into the last value.
- Fixed: adding an id or setting one property no longer reformats the rest of the front matter (long values folded, lists re-spaced), and a byte-order mark stays at the start of the file.
- Fixed: a note saved in a legacy encoding (Windows-1252, UTF-16) is no longer rewritten with its accents destroyed. Basalt reads and indexes it, never writes to it, and says so (in the server log, and with a 409 on save) until it is saved as UTF-8.
- Fixed: when an Obsidian edit to a note's last line and a Basalt append (quick capture, the agent) meet, the two lines stay separate instead of being joined into one.

## CLAUDE.md changes to apply (exact text, and where)
- In "One shared vault with Obsidian", replace the paragraph starting **First index stamps every note** with:

  > **First index stamps every note** — when it can do so without changing anything else: any note without `id: n-…` front-matter gets one line, `id: n-…`, added after its opening fence (or a new block, CRLF and BOM kept). `stampId` (`packages/core/src/frontmatter.ts`) refuses, and the note is indexed as it is, when the front matter does not parse, is not a mapping (prose between two `---` rules, a bare list), carries the user's own non-text `id:`, or the file is not UTF-8. Such a note keeps the id its path already had (the notes table at boot, the index live), so task objects stay attached; it is not rename-safe outside Basalt. A file that is not UTF-8 is never written at all: `write()` answers 409. That is what keeps renames link-safe (task objects key on the note id), and it means pointing Basalt at a fresh vault modifies every file in it once. `scripts/merge-vaults.mjs` is the one-off that folded Basalt's old copy into the Obsidian vault (newest-wins per file, carrying ids across).

- In "Conventions & gotchas", after the bullet **Files in the vault are replaced, never rewritten in place**, add:

  > - **Never rewrite bytes that were not parsed.** `updateFrontmatter` edits only the lines of the keys it changes and reads its result back; if it would not read back as exactly the new data with the body byte-identical, the note is returned unchanged. Splices (`diffSplice`) are bounded on whole code points — Yjs turns a split surrogate pair into U+FFFD — and `updateDocContent` throws rather than leave a doc that reads otherwise. `mergeText` merges with every line terminated (Obsidian writes no final newline).

## Not fixed (and why) / needs Jules
- STO-005 acceptance "tasks in a CRLF note are parsed and can be toggled, and the toggled file stays CRLF": the task/heading parse side (`TASK_RE`/`HEADING_RE`/`TASK_LINE_RE` stop at `\r`) is COR-012, S10's ticket. Front-matter parsing and stamping of CRLF notes are fixed here.
- Not in my tickets, noticed: a heading on line 1 right after a BOM in a note with no front matter is not parsed as a heading (`parse.ts` `HEADING_RE`). Once stamped, the BOM sits before the fence and the note reads fine. Parser side (S10 area).
- A note that cannot be stamped (unparseable YAML, non-mapping block, numeric `id:`, not UTF-8) is indexed with a path-kept id, but nothing in the UI says so — only the server log. Renaming such a note outside Basalt gives it a new id. A visible "front matter does not parse" / "not UTF-8" hint on the note would be a web follow-up.
- Typing in a non-UTF-8 note in the editor: checked on the scratch server — the save gets the 409, the editor shows its generic red "save failed", the file stays byte-identical. The editor does not show the reason ("not UTF-8, save it as UTF-8 first"); that and what happens to the unsaved typing are web-side (WEB-002 territory), not changed here.
