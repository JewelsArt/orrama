## Built
- The app starts, watches and stops its own server and keeps its secrets; links leave the window,
  downloads land in Downloads; the bundled pages (commit 9b5c26d).
- One Orrama at a time: the single-instance plugin (commit 7c20293).

How it behaves, in short (details in `apps/desktop/README.md`):
- **Start:** `node server.mjs` with the contract's environment (none of the person's `ORRAMA_*`), stdout
  and stderr appended to `<data dir>/logs/server.log` (the shell's own lines there too, `"name":"shell"`).
  The window shows "Starting Orrama…" and moves to `http://localhost:<port>` only when `/api/health`
  answers as Orrama **with this launch's id**. With 2A's bundle it answers in ~1 s on this Mac.
- **Port:** stored port if free → 4623 if free → a system port; kept in `desktop.json`.
- **Crash:** restart after 1 s, 5 s, 15 s; a 4th exit within a minute → "Orrama couldn't start"
  (Try again, Show the log). A start silent for 5 minutes counts as an exit.
- **Quit:** stdin closed, 10 s, then kill. **Shell killed:** its stdin closes, the server stops itself.
- **Secrets:** made once; a folder with `basalt.db` never gets new ones ("Orrama can't read its key",
  nothing started, nothing written).

## The contract: what I read into it, and one change in order
- **Port order is stored → 4623 → system**, not "4623 if free, else the stored one": a port must not
  move back to 4623 once another was stored, because the ChatGPT callback is registered per port and the
  session cookie is named after it. Same result as the contract on a first launch and on Jules's Mac.
  Shell-only; 2A is not affected.
- Besides every `ORRAMA_*`, the shell also drops `BASALT_*` (the server refuses to boot beside one),
  `NODE_OPTIONS` and `NODE_PATH` from the person's environment; `PORT`/`HOST` are always the shell's.
- `ORRAMA_DATA_DIR` set for a run also gives the Credential Manager / Keychain entry its own name
  (`server secrets for <path>`), so a test run never reads the real one.

## Waits for Windows, and how to prove it
On Windows nothing has run yet. After the Actions reset, once 2D's `release.yml` gives the first `.exe`,
in the UTM VM (D9) or the friend's PC:
1. Install, open: "Starting Orrama…", then first run. `%LOCALAPPDATA%\com.orrama.desktop\` holds
   `desktop.json` and `logs\server.log`, and **no** `secrets.json`; Credential Manager → Windows
   Credentials lists `server secrets.com.orrama.desktop`.
2. No console window appears for node.exe.
3. Open Orrama again from the Start menu: the first window comes forward, Task Manager shows one node.exe.
4. End `Orrama.exe` in Task Manager: node.exe disappears within a few seconds, and the log ends with
   "stdin closed: closing" (no `basalt.db-wal` left).
5. End node.exe in Task Manager: the window shows "Starting Orrama…" and comes back.
6. Close the window: node.exe exits (log: "the server stopped (exit status: 0)").
7. Settings → Source code, a mail link, Sign in with ChatGPT: each opens in the browser; a document's
   Download lands in Downloads.
8. Delete the Credential Manager entry, open Orrama: "Orrama can't read its key", nothing started.
CI's share: a `windows-latest` job running `cargo test --lib` (above); green means the secret store,
port rule, environment, routing and the supervisor (stdin stop of a Node child) pass on Windows.
